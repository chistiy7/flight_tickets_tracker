# Свой парсер: сбор в склад и опрос склада

Партнёрские API отдают либо кэш чужих поисков (Travelpayouts), либо нероссийских
перевозчиков (Duffel). Рублёвые тарифы Азимута, Red Wings и российских OTA не отдаёт
никто — их видно только на страницах продавцов. Поэтому в трекере предусмотрен контур
«собираем сами»: парсер наполняет **склад офферов**, а прогон трекера этот склад
опрашивает.

## Почему сбор нельзя делать внутри прогона

Соблазн понятен: провайдер идёт на сайт прямо во время поиска. Так делать не нужно.

- **Скорость.** Один запрос к странице — от секунды (внутренний JSON) до десятков секунд
  (headless-браузер с прогревом cookies). План запросов трекера — `tbs-tracker routes
  --queries`, это сотни пар «плечо + окно дат». Прогон превращается в многочасовой скрейпинг.
- **Надёжность.** Парсер ломается: редизайн, смена схемы ответа, капча, блокировка IP.
  Внутри прогона одна заблокированная площадка портит весь результат поиска; снаружи —
  просто не обновляет часть склада, а прогон работает на том, что собрано раньше.
- **Темп.** Уважительный парсинг — это низкая частота, паузы, ретраи и очередь. Это
  расписание парсера, а не расписание поиска маршрута.
- **История.** Склад копит цены по каждому рейсу, а не только по итоговым цепочкам. По нему
  видно, дорожает ли конкретный рейс, даже если он ни в одну цепочку не попал.

Отсюда разделение на две команды:

```bash
tbs-tracker collect            # сбор: источники → склад офферов
tbs-tracker run                # поиск: склад (+ другие источники) → цепочки → алерты
tbs-tracker collect --status   # что лежит на складе и насколько оно свежее
```

## Возраст записи — часть цены

Единственное, что склад обязан делать честно, — не выдавать старое за покупаемое.
Провайдер `collector` понижает тип цены по возрасту записи:

| Возраст записи | Что с ценой |
|---|---|
| до `fresh_minutes` (по умолчанию 120) | остаётся такой, какой собрали: `live` — живая, `estimate` — оценка |
| дольше `fresh_minutes` | становится `cached` — наблюдение, а не предложение |
| дольше `max_age_minutes` (по умолчанию 1440) | не отдаётся вовсе, вычищается при следующем `collect` |

Собранная утром «живая» цена к вечеру живой быть перестаёт: рейс мог подорожать или
исчезнуть. Поэтому в деталях варианта у такого плеча видно `собрано 9 ч назад`, а алерт по
неживой цене, как и раньше, требует подтверждения.

Оценка (`estimate`) не становится живой ценой от того, что её только что собрали: цену
маршрутки через Верхний Ларс никакой парсер не превратит в оффер к покупке.

## Подключение

```yaml
providers:
  collector:
    enabled: true
    db_path: data/collector.sqlite3   # склад в файле рядом с трекером
    # url: http://127.0.0.1:8899/prices   # либо парсер отдельным сервисом
    # token_env: COLLECTOR_TOKEN
    fresh_minutes: 120
    max_age_minutes: 1440
```

Два режима, оба читают одно и то же:

- **Файл** (`db_path`) — парсер и трекер живут на одной машине. Самый простой вариант.
- **HTTP** (`url`) — парсер вынесен в отдельный сервис (другая машина, прокси, свой
  язык). Опрос своего склада не тратит бюджет внешних запросов: `max_requests_per_run`
  на него не расходуется.

Провайдер `collector` не парсит сам и в сеть за ценами не ходит. Он либо читает файл, либо
спрашивает ваш сервис.

## Кто наполняет склад

**Вариант 1. Встроенный сбор.** `tbs-tracker collect` опрашивает включённые провайдеры и
складывает результат. Здесь же работает `airline_direct` — это уже парсер, только
декларативный: внутренний JSON-эндпоинт календаря цен и пути до полей описываются в
конфиге, без кода. Для сайтов, которые отдают цены в JSON (а таких большинство), своего
кода писать не нужно.

**Вариант 2. Свой парсер.** Когда нужен headless-браузер, прокси или разбор HTML,
парсер живёт отдельно и пишет в склад сам. Ему нужно уметь одно из двух: писать строки в
таблицу `offers` или отвечать на HTTP-запрос трекера.

### Контракт HTTP

Трекер делает `GET {url}` с параметрами:

| Параметр | Пример | Смысл |
|---|---|---|
| `origin`, `destination` | `MOW`, `TBS` | IATA-коды плеча |
| `date_from`, `date_to` | `2026-10-05` | окно дат вылета |
| `modes` | `air,bus` | какие режимы передвижения интересны |
| `passengers` | `1` | число пассажиров |
| `max_age_minutes` | `1440` | старше этого отдавать не нужно |

Ответ — `{"offers": [...]}` (или просто список). Поля оффера:

```json
{
  "mode": "air",
  "price": 12900,
  "currency": "RUB",
  "carrier": "A4",
  "flight_number": "A4451",
  "depart": "2026-10-06T09:00:00+03:00",
  "arrive": "2026-10-06T12:30:00+04:00",
  "duration_min": 210,
  "transfers": 0,
  "baggage_included": false,
  "payment_channel": "ru_card",
  "price_kind": "live",
  "deep_link": "https://azimuth.aero/booking?...",
  "link_kind": "booking",
  "booking_ref": null,
  "parser": "azimuth",
  "collected_at": "2026-10-01T08:15:00+00:00"
}
```

Обязательны только `mode`, цена (`price` + `currency`, либо сразу `price_rub`) и
`collected_at`. Пересчёт валюты в рубли — забота трекера, курс он берёт из своих настроек.
`parser` попадает в имя источника (`collector:azimuth`), чтобы в отчёте было видно, кто
принёс цену. `link_kind` определяет подсказку в отчёте: `booking` — «купить», `search` —
«искать» (нужный рейс ещё предстоит найти), `info` — «смотреть».

### Контракт таблицы

Схема создаётся сама при первом `collect` (`src/tbs_tracker/collector.py`). Ключ строки —
«личность рейса» без цены: плечо, перевозчик, номер, время вылета и источник. Повторный
сбор того же рейса обновляет цену, а не добавляет строку, иначе подорожавший рейс вечно
выигрывал бы по старой записи.

Писать можно чем угодно, что умеет SQLite:

```python
from tbs_tracker.collector import CollectorStore
from tbs_tracker.models import Leg, LinkKind, Mode, PriceKind

with CollectorStore("data/collector.sqlite3") as store:
    store.put([
        Leg(
            origin="MOW", destination="TBS", mode=Mode.AIR,
            price_rub=12900, source="parser:azimuth",
            carrier="A4", flight_number="A4451",
            depart=depart, duration_min=210,
            price_kind=PriceKind.LIVE,
            deep_link="https://azimuth.aero/booking?...",
            link_kind=LinkKind.BOOKING,
        )
    ])
```

## Границы: что парсер решает, а что нет

Парсер снимает ограничение «нет партнёрского договора — нет цены», но не снимает
остальные.

- **ToS и антибот.** Автоматический сбор с сайтов авиакомпаний и OTA почти всегда
  противоречит их правилам, а крупные площадки закрыты антибот-системами. Работающий
  подход — низкая частота, уважение к `robots.txt`, отсутствие обхода капчи и сбор только
  цен (факт), а не чужого контента. Обход защиты — это гонка вооружений, блокировки и
  юридический риск, особенно при коммерческом использовании.
- **Стоимость.** Резидентные прокси и браузерные воркеры стоят денег и времени
  сопровождения. Прежде чем поднимать инфраструктуру, стоит сравнить: для многих площадок
  партнёрский API дешевле собственного парка прокси.
- **Точечность выигрывает.** Смысл парсера — там, где API не существует: 3–5 перевозчиков
  прямых рейсов и пара российских OTA. Пытаться спарсить весь рынок бессмысленно: широкое
  покрытие уже даёт Travelpayouts, хоть и кэшем.
- **Проверка перед покупкой остаётся.** Даже собранная минуту назад цена — это цена
  страницы, а не выписанный билет. Итоговое подтверждение всегда на сайте продавца, и
  ссылка на него хранится в оффере.
